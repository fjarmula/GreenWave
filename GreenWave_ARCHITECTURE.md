# ER-GreenWave: Emergency Response GreenWave System

**Project developed for the "Open Data App" Hackathon (Kraków)**

ER-GreenWave is a proof-of-concept (PoC) platform demonstrating dynamic
routing and preemptive traffic-light clearing for emergency vehicles.
Using open spatial data from the City of Kraków, the system creates
temporary "green corridors" (life corridors) to reduce emergency
response times without compromising civilian traffic safety.

## 1. Glossary and Acronyms

- **TTI (Time to Intersection):** The dynamically calculated time
  remaining before the emergency vehicle reaches a specific
  intersection.
- **ITS (Intelligent Transportation System):** Centralized city
  systems that manage traffic lights. In Kraków, this refers to the
  STeR system.
- **MSIP (Miejski System Informacji Przestrzennej):** Kraków's
  official municipal spatial information system. In this project it is
  the publisher of the municipal street registry (`Ulice.geojson`) and
  of the other Kraków open-data files recorded in the raw-data manifest.
  It is not the source of the road network or of the traffic signals
  (these come from OpenStreetMap, see section 6, decision 6).
- **ZDMK (Zarząd Dróg Miasta Krakowa):** Kraków's municipal road
  authority; named as a publisher of the bus-lane data that is recorded
  in the manifest but not used by the PoC.
- **INT-xxxx:** An intersection identifier generated by the ETL
  (`INT-0001`..`INT-0534`): a signalised junction, a mid-block signal or
  a standalone signalised pedestrian crossing.
- **D_v / D_u:** The delay of one intersection without priority (35 s
  per kind in the current configuration), applied once per unique
  `INT-xxxx` whose controlled approach the route passes.
- **Datex II / NTCIP 1211:** Standards associated with communication
  and priority control in intelligent transportation systems.
- **SSE (Server-Sent Events) / WebSockets:** Technologies for
  streaming real-time data from the backend to the frontend,
  respectively unidirectionally or bidirectionally.
- **PoC (Proof of Concept):** A scaled-down implementation built to
  validate core logic and technical feasibility.
- **ER Green Wave mode:** The per-run choice `green_wave_mode`
  (`ENABLED | DISABLED`). Enabled is the priority corridor described
  throughout this document; disabled simulates the same vehicle crossing
  signals in standard traffic (section 3, model 3), for comparing final
  travel times one run at a time.

## 2. Architecture and Technology Stack

The project uses a decoupled architecture with a JSON-based
publish/subscribe contract. This supports rapid iteration, clear
separation of concerns, and straightforward integration with AI coding
assistants.

### Technology Stack

- **Backend:** Python and **FastAPI** (asynchronous event loop), with
  dependencies managed by **`uv`**.
- **Data processing engine:** **GeoPandas**, **Polars**, and
  **NetworkX** for graph-based pathfinding and spatial joins.
- **Frontend:** **Next.js** (React), **Tailwind CSS**, and
  **shadcn/ui** for dashboard development; run locally for the demo.
- **Mapping engine:** **MapLibre GL JS** (free, token-free fork of Mapbox GL; OSM-based tiles) for GPU-accelerated WebGL
  rendering of vehicle routes and intersection states.

### Architectural Decisions: Why?

1.  **Mocking the ITS controller:** The PoC does not interface directly
    with physical traffic lights because physical overrides are
    safety-critical. Instead, the system acts as an analytical layer
    that sends standardized priority requests to a mocked central ITS.
2.  **JSON contracts over WebSockets/SSE:** The frontend is passive and
    stateless. It consumes one event per simulated second (1 Hz at
    normal speed, up to 10 Hz at the fastest playback) and renders the
    interface, keeping UI complexity low.
3.  **Precomputed graph (ETL):** The pinned BBBike OpenStreetMap
    extract (road network and traffic signals) and the Kraków open-data
    street registry (`Ulice.geojson`), both tracked with hashes in
    `backend/data/raw/MANIFEST.json`, are processed by an offline ETL
    step (output cached in `backend/data/processed/`, never committed)
    into a directed NetworkX graph (`MultiDiGraph`, EPSG:2178 metres)
    plus the intersection, signal-approach and neighbour tables that the
    server loads once at startup. The loader refuses to start when an
    artifact is missing, was built from a different manifest, or comes
    from a different ETL run (per-artifact hashes); there is no
    fallback. Performing real-time pathfinding directly on raw GIS data
    would be too slow.
4.  **Corridor batching (cascade mode):** Clearing a single intersection
    on a dense street (such as Aleje Trzech Wieszczów) is ineffective if
    traffic is blocked at another intersection 150 m ahead. The engine
    groups consecutive intersections along the active route (along-route
    stop-line distance **d <= 250 m**, inclusive) and triggers them
    together. The ETL ships a candidate table of approach pairs within
    250 m by shortest drive (`approach_neighbours`); it is only a
    candidate set, and the engine decides with the along-route distance
    on the actual route.

## 3. Mathematical Models and Core Logic

### Time to Intersection (TTI)

TTI is recalculated every simulated second (one engine step and one streamed tick) to drive the intersection state machine:

$$\mathrm{TTI}_i = \frac{d_i}{v_{\mathrm{avg}}}$$

Where:
- $d_i$ is the remaining distance (in metres, calculated in EPSG:2178) along the active route polyline to the first controlled approach stop line of intersection $i$.
- $v_{\mathrm{avg}}$ is the smoothed velocity of the ambulance (in $\text{m/s}$), computed as an exponential moving average $v_{\mathrm{avg}, t} = 0.25 \cdot v_t + 0.75 \cdot v_{\mathrm{avg}, t-1}$ (initialized to $v_0$ on the starting edge and floored at $5.0\text{ m/s}$ to prevent division by zero).

### Travel-Time Estimation Algorithm

The system compares normal routing with ER-GreenWave routing to estimate potential time savings (converting $L_e$ in metres and speeds in $\text{km/h}$ to seconds via $\text{speed}_{\mathrm{m/s}} = \text{speed}_{\mathrm{km/h}} / 3.6$):

#### 1. Normal travel time (without priority)

$$T_{\mathrm{normal}} = \sum_{e \in \mathrm{Edges}} \left( \frac{L_e \cdot \mu_{\mathrm{traffic}} \cdot f_{\mathrm{lane}}(e) \cdot f_{\mathrm{surface}}(e)}{V_e} + n_e \cdot s_{\mathrm{normal}} \right) + \sum_{u \in \mathrm{Intersections}} D_u$$

Where $V_e$ is the edge speed (`speed_kmh`: the OSM `maxspeed` where it parses, otherwise a road-class default, recorded in `speed_source`), $\mu_{\mathrm{traffic}} \in [1.0, 3.0]$ is the traffic-density multiplier ($\mu_{\mathrm{traffic}} = 1.0$ is free-flow; $1.5$ increases edge traversal time by 50%), and $D_u$ is the delay of intersection $u$ (`delay_seconds` in the ETL's `intersections` table). Signalised junctions, mid-block signals and pedestrian crossings have independent configuration keys; each is provisionally 35 s. These values are modeling assumptions, not empirical measurements. Calibration is deferred to a dedicated modeling task after dynamic ambulance dispatch is implemented and before final end-to-end performance evaluation. $D_u$ is applied once per unique intersection (`INT-xxxx`) whose controlled approach the route passes: a route that passes two approaches of one intersection pays it once, and the per-signal `signal_approaches.delay_seconds` is never summed along a route.

Road attributes per directed edge (ETL, `network_edges.parquet`): $f_{\mathrm{lane}}(e) = 1.15$ when `lanes_per_direction == 1`, else 1; $f_{\mathrm{surface}}(e) = 1.3$ when `surface_class == "unpaved"`, else 1; $n_e$ is `calming_count` (OSM `traffic_calming` points on the edge) and $s_{\mathrm{normal}} = 3\text{ s}$ per feature. An unknown attribute has no effect. Values and evidence: `docs/adr/0005-road-attribute-time-factors.md`.

#### 2. ER-GreenWave travel time (with priority)

$$T_{\mathrm{greenwave}} = \sum_{e \in \mathrm{Edges}} \left( \frac{L_e}{V_{\mathrm{ambulance}}(e)} + n_e \cdot s_{\mathrm{ambulance}} \right) + \sum_{u \in \mathrm{Intersections}} D_{\min}$$

Where $V_{\mathrm{ambulance}}(e) = \min(\max(1.3 \cdot V_e \cdot b(e),\; 30\text{ km/h}),\; 90\text{ km/h})$, $b(e)$ is the **largest** applicable boost (not the product; 1 when none applies): 1.05 on a `bus_lane` edge, 1.05 on a `tram_track` edge; $s_{\mathrm{ambulance}} = 2\text{ s}$ per calming feature; and $D_{\min} = 3\text{ s}$ is applied once per unique intersection (`INT-xxxx`) whose controlled approach the route passes, by the same rule as $D_u$.

One edge-time function (`backend/src/greenwave/routing/edge_times.py`) drives route choice (minimum ambulance edge time), both estimates and simulated motion: on each edge the simulated ambulance moves at the effective speed $L_e / t_a(e)$ with $t_a(e) = L_e / V_{\mathrm{ambulance}}(e) + n_e \cdot s_{\mathrm{ambulance}}$, so calming seconds are spread over the edge and the simulated trip matches $T_{\mathrm{greenwave}}$, including a route ending exactly on a stop line. All factors are `GREENWAVE_SIM_*` settings; 1.0 / 0 s makes an attribute neutral.

In the simulation the ambulance never stops for $D_{\min}$: it spends it as a rolling slowdown over the last `greenwave_approach_distance_m` (60 m) before each intersection's first controlled stop line (never starting before the previous intersection's first stop line), at a constant reduced share of its own speed that adds exactly $D_{\min}$, never below `greenwave_min_rolling_speed_kmh` (15 km/h). When that window is too short to absorb $D_{\min}$ at or above the floor (close junctions, a route starting near a line), the slowdown continues past the line at the floor speed until $D_{\min}$ is spent. The trip therefore still takes $T_{\mathrm{greenwave}}$. Separately, the ambulance leaves a first stop line only once every route vehicle light at that line was last **shown** green (section 4, signal phases). Priority normally turns green long before, so this hold changes nothing; it only matters when priority is requested too late (for example a route that starts just before a junction), where the ambulance waits at the line instead of driving through red. That hold is the only time an enabled run shows 0 km/h before arrival.

#### 3. Standard-traffic crossing (ER Green Wave disabled)

With `green_wave_mode: "DISABLED"` the route and the open-road motion are exactly those of model 2; only signalised stop lines are crossed differently. At **every** controlled stop line of the route (including lines inside a junction), the engine samples the simulated route movement colour (section 4, signal phases) at the exact simulated time the vehicle reaches the line:

1. **`GREEN`:** the vehicle drives on at $V_{\mathrm{ambulance}}(e)$; no penalty.
2. **`RED`, `YELLOW`, or no supported route vehicle signal:** the vehicle rolls one controlled crossing of $L_c$ = `standard_crossing_distance_m` (default 30 m) without stopping. Its extra cautious time $C_u = c \cdot D_u \cdot \mu_{\mathrm{traffic}}$ (cautious red-light entry while traffic forms a life corridor, $c$ = `standard_clearance_factor`, default 1.0) is spread over that distance: a segment of length $d$ on an edge with ordinary limit $v = \min(V_{\mathrm{ambulance}}(e), V_e)$ takes
   $$\frac{d}{v} + C_{\mathrm{remaining}} \cdot \frac{d}{L_{\mathrm{remaining}}},$$
   so the speed is positive, never above $v$, and carries across edge ends.

A later stop line replaces an active crossing with its own decision (a fresh crossing if it is not green). Each intersection's route signals share one cycle phase, so the lines of one through movement show the same colour. The crossing is a modelling boundary (the ETL has no junction exit geometry), and $c$, $L_c$ are PoC assumptions, not measured Kraków values; $L_c$ is strictly positive and both are finite. There is no separate disabled-mode estimate: the run's `total_time_elapsed_sec` is the exact simulated arrival, and `current_time_saved_sec` compares it with $T_{\mathrm{normal}}$ in either mode. Implementation: `backend/src/greenwave/simulation/motion.py`.

## 4. Data Flow and JSON Protocols

The system uses explicit JSON schemas as the API contract between the
engine and the dispatcher dashboard. Only one active operation runs at a
time in the PoC: a single run, or a comparison pair started together by
`POST /api/v1/simulation/compare/start` and advanced in lockstep (ADR
`docs/adr/0008-live-comparison-pair.md`). Starting anything cancels the
whole previous operation (`SUPERSEDED`), and stopping either pair member
stops both.
All outputs are simulated inputs and include `"is_simulated": true`.
Every response and stream event also carries `"schema_version": "1.0"`.
The contract is frozen as `contract-v1` (see `docs/adr/0003-simulation-contract-v1.md`).
The intersection ids and names in the examples are real ETL output (two
consecutive junctions on Aleja 29 Listopada, about 152 m apart by
shortest drive); coordinates, times and speeds are illustrative.

### Intersection State Machine & Cascade Rules

Each intersection (`INT-xxxx`) along the active route transitions through
four states (`NORMAL | CLEARING | PRIORITY_GREEN | RECOVERY`), with a
separate boolean flag (`is_cascade: true | false`) indicating whether
the transition was triggered early by an upstream intersection within
`d <= 250 m` along the route:

1. **`NORMAL -> CLEARING`:** Triggered when $\mathrm{TTI}_i \le 40\text{ s}$
   (`is_cascade: false`), OR when an upstream intersection $j$ along the
   route enters `CLEARING` **because its own** $\mathrm{TTI}_j \le 40\text{ s}$
   (`is_cascade: false`) and the along-route distance from the stop
   line of $j$'s controlled approach to the stop line of $i$'s is
   $\le 250\text{ m}$ (`is_cascade: true`). Cascade is **one hop only**:
   an intersection that entered `CLEARING` through a cascade
   (`is_cascade: true`) never triggers a further cascade. Cascade looks
   only ahead along the route (never at an intersection already passed
   or behind $j$), uses the inclusive 250 m threshold measured from
   $j$ itself, and is disabled when `enable_cascade_mode` is `false`.
   Every other intersection still enters `CLEARING` by its own TTI. If an
   intersection reaches $\mathrm{TTI} \le 40\text{ s}$ in the same tick in
   which it would be cascaded, its own TTI wins (`is_cascade: false`).
   `CLEARING_CASCADE` is **not** a state; a cascaded intersection is
   `state: "CLEARING"` with `is_cascade: true`.
2. **`CLEARING -> PRIORITY_GREEN`:** Triggered when $\mathrm{TTI}_i \le 25\text{ s}$.
3. **`PRIORITY_GREEN -> RECOVERY`:** Triggered when the ambulance has
   passed the intersection's last controlled approach stop line
   ($d_i \le 0\text{ m}$), but never while it is still stopped on that
   line (held for green, also for another
   intersection sharing the line) and never in the tick that carries it
   across the line: the dashboard animates the vehicle across each tick
   under that tick's lights, so priority is released on the following
   tick, once the vehicle is visibly past. A destination exactly on the
   last stop line is released once the vehicle has stopped there.
4. **`RECOVERY -> NORMAL`:** Triggered $15\text{ s}$ after entering
   `RECOVERY`.

`is_active_corridor` is `true` exactly when `state` is `CLEARING` or
`PRIORITY_GREEN` (computed by the backend).

With `green_wave_mode: "DISABLED"` none of these transitions happen: every
intersection stays `NORMAL` (it is only marked passed), nothing cascades
and no ITS dispatch is made, whatever `enable_cascade_mode` says.

### Phase 0: Incident Dispatch (Frontend → Backend)

The operator picks a vehicle type (`AMBULANCE | FIRE_TRUCK | POLICE_CAR`) and
the incident location (local address search or a map click). The backend
ranks that type's stations and the run then goes from the fastest one to the
incident (additive to contract v1, `docs/adr/0006-incident-dispatch-contract.md`).

```
GET  /api/v1/stations                    -> StationsResponse (all types, by station_id)
GET  /api/v1/geocode?q=<2-100>&limit=<1-10, default 8>
                                         -> GeocodeResponse ({label, position} results)
POST /api/v1/dispatch/rank {incident, vehicle_type}
                                         -> DispatchRankResponse (1-3 candidates, best first,
                                            incident_snapped, station_at_incident)
```

- **Data:** the ETL `places` step writes `stations.parquet` (ambulance bases,
  hospital emergency departments, fire and police stations from OSM, with
  exclusion and inclusion lists in `etl/config.py`) and `addresses.parquet`
  (unique labels, locality added outside Kraków or on a repeat).
- **Ranking:** a reversed Dijkstra from the incident over the routing weight
  shortlists `dispatch_shortlist_size` (5) stations; each gets the real
  `plan_route` + route model + `estimate_times`, ranked by
  `(greenwave_seconds, station_id)`. The displayed time is therefore the
  `estimated_greenwave_time_sec` the run reports. A station on the incident's
  own node is returned as `station_at_incident` and skipped. Errors:
  `DESTINATION_OFF_NETWORK`, `NO_STATION_REACHABLE` (422).
- **Snapping:** all endpoints (start, incident, stations) snap only to the main
  strongly connected component of the road graph, so a point next to a road
  island (e.g. a pedestrian street) still gets a route both ways.
- **Mock transport:** no address search; straight-line nearest station from
  the committed `frontend/src/data/stations.snapshot.json`, labelled
  "Approximate (mock)".

### Phase 1: Route Initialization (Frontend → Backend)

**Endpoint:** `POST /api/v1/simulation/start`

Called when the operator starts the run: `origin` is the chosen station and
`destination` the incident. `traffic_density_multiplier` must be in
`[1.0, 3.0]`. `vehicle_type` is optional (default `AMBULANCE`) and is reported
in the ITS payload; it changes nothing else in the engine. `green_wave_mode`
is optional (`ENABLED | DISABLED`, default `ENABLED`, so older clients keep the
priority corridor); `DISABLED` selects the standard-traffic crossing (section
3, model 3) and forces cascade off.

**Request:**

```json
{
  "simulation_id": "SIM-20261025-01",
  "origin": {
    "lat": 50.0612,
    "lng": 19.9571
  },
  "destination": {
    "lat": 50.0134,
    "lng": 19.9982
  },
  "traffic_density_multiplier": 1.5,
  "enable_cascade_mode": true,
  "playback_speed": 1,
  "vehicle_type": "AMBULANCE",
  "green_wave_mode": "ENABLED"
}
```

`simulation_id` is chosen by the client and must match
`^[A-Za-z0-9_-]{1,64}$`. `playback_speed` is optional (integer `1..10`,
default `1`): every simulated second is one engine step and one streamed
`SIMULATION_TICK` at every speed; playback only shortens the wall-clock
gap between ticks to `1 / playback_speed` s (1 s at 1x, 0.2 s at 5x,
0.1 s at 10x). Playback is not an engine input, so trajectories, stop-line
crossings, signal phases, arrival and KPIs are identical at every speed.
This supersedes the earlier 1 Hz batching (ADR 0003, D9).

| `error_code` | HTTP | When |
|---|---|---|
| `ORIGIN_OFF_NETWORK` | 422 | Origin farther than the snap limit (150 m, section 6) from the network |
| `DESTINATION_OFF_NETWORK` | 422 | Same for the destination |
| `NO_ROUTE` | 422 | Both ends snap but no route connects them |

(multiplier outside `[1.0, 3.0]`, bad `simulation_id` pattern,

**Comparison pair:** `POST /api/v1/simulation/compare/start` (ADR 0008,
additive to contract v1) takes the same fields minus `green_wave_mode`, plus
`enabled_simulation_id` and `disabled_simulation_id` (must differ), and returns
`{"schema_version", "is_simulated", "enabled", "disabled"}` with the two start
responses above. Both runs plan the same route; one shared loop steps every
unfinished member once per interval, so both share each simulated second. Each
run keeps its own stream and stop endpoint; stopping either stops both (a
member that already completed keeps its completed terminal). Errors are the
same as for `/start`, and a failed plan starts neither run.

### Phase 2: Real-Time Telemetry Stream & Control (Backend ↔ Frontend)

- **Stream Endpoint (SSE, one tick per simulated second):** `GET /api/v1/simulation/{simulation_id}/stream`
- **Stop Endpoint:** `POST /api/v1/simulation/{simulation_id}/stop`

The frontend consumes the Server-Sent Events (SSE) stream to animate the
MapLibre vehicle marker and update dashboard KPIs. The marker slides to
each tick's position over one tick interval (`1000 / playback_speed` ms),
always starting from the previous tick's position, while the tick's signal
phases are shown as soon as it arrives; a late or bunched tick therefore
never leaves the marker behind the lights. The offline mock transport
follows the same one-tick-per-simulated-second rule and intervals.
Ambulance `status` is an enum of
`EN_ROUTE | APPROACHING_INTERSECTION | CROSSING_INTERSECTION | ARRIVED`;
`CROSSING_INTERSECTION` covers, in an enabled run, the $D_{\min}$ slowdown
and any hold at a stop line and, in a disabled run, the whole controlled
crossing. `speed_kmh` is the distance
actually driven in that simulated second, including the arrival tick.

The stream carries a discriminated union on `event_type`:
`SIMULATION_TICK`, `ITS_DISPATCH`, `SIMULATION_COMPLETED`,
`SIMULATION_CANCELLED` (`reason: STOPPED | SUPERSEDED | SERVER_ERROR`). Every event has
`schema_version`, `is_simulated`, `simulation_id`, `tick` and `timestamp`
(wall-clock UTC at emission; simulated time is
`kpi_metrics.total_time_elapsed_sec`).

**SSE framing** (not expressible in OpenAPI, so normative here): the first
frame is `retry: 2000`. Each event is one frame with `event:` = its
`event_type`, `id:` = its `tick` (non-decreasing; ticks start at 1, an
`ITS_DISPATCH` shares the id of the tick that produced it and precedes that
tick's `SIMULATION_TICK`; a terminal event repeats the last tick id) and
`data:` = the JSON of one event model. The server closes the stream after
a terminal event (`SIMULATION_COMPLETED` or `SIMULATION_CANCELLED`).
A subscriber first receives the latest snapshot, then live events; a
reconnect resumes at "now" without replay. The run is server-authoritative:
it starts on `POST /start` and ticks whether or not anyone listens. After
`ARRIVED` the engine keeps ticking until every intersection is `NORMAL`
(at most 15 s), then emits `SIMULATION_COMPLETED`. An ended session stays
readable while it is among the most recent sessions (engine setting
`retained_session_limit`, default 4, which always keeps the active run); an
older id answers 404 `SIMULATION_NOT_FOUND`. Each run emits exactly one
terminal event. `POST /stop` returns `StopResponse`
(`{"schema_version": "1.0", "is_simulated": true, "simulation_id": ..., "status": "STOPPED"}`).

```json
      "signal_key": "OSM-L1214",
      "kind": "VEHICLE",
      "color": "YELLOW",
      "position": { "lat": 50.0663, "lng": 19.9218 },
      "accessible_label": "Simulated vehicle signal OSM-L1214 at INT-0360: yellow"
    },
    {
      "intersection_id": "INT-0360",
      "signal_key": "OSM-L1214",
      "kind": "PEDESTRIAN",
      "color": "RED",
      "position": { "lat": 50.0663, "lng": 19.9218 },
      "accessible_label": "Simulated pedestrian signal OSM-L1214 at INT-0360: red"
    }
  ]
}
```

Every tick lists **all** route intersections in route order.
`tti_seconds` is an integer (rounded) and `null` once the intersection has
been passed; `name` is nullable. `total_time_elapsed_sec` advances by
1 per tick at every playback speed.

`signal_phases` (default `[]`) is a deterministic, **simulated** explanatory
layer, never a live or measured signal state (`backend/src/greenwave/simulation/phases.py`).
One pure programme (`phase_decisions` / `route_movement_color_at`) drives
both disabled-mode motion (sampled at the exact time a stop line is reached)
and these indicators (sampled at the end of each tick):

- Indicators per signal node of each route intersection, positioned at the
  node's processed OSM coordinates (`signal_approaches.parquet` `lon`/`lat`,
  required and range-checked by the loader). `traffic_signals` nodes show a
  `VEHICLE` and a `PEDESTRIAN` indicator, `pedestrian_crossing` nodes a
  `PEDESTRIAN` indicator only, and any other node type or a node controlling
  no edge shows none. An intersection without known signal nodes yields no
  indicator; no position is ever synthesised. `kind` is `VEHICLE | PEDESTRIAN`,
  `color` is `RED | YELLOW | GREEN`, `signal_key` is stable within the
  intersection, and `(intersection_id, signal_key, kind)` is unique per tick.
- Normal programme: a signal's movement group is its controlled approach
  identity (sorted controlled-edge ids), except that the route's vehicle
  signals of one intersection form a single group (its through movement).
  The sorted groups take two cycle slots by ordinal modulo two, each green
  `signal_green_seconds` (30), yellow `signal_yellow_seconds` (3), all-red
  `signal_all_red_seconds` (2). A pedestrian crossing the arm a node controls
  is green only while the other slot has green and every vehicle light of
  its own slot shows red.
- Priority: only a route **vehicle** signal (a vehicle-capable node
  controlling the route's stop-line edge) can be made green. `CLEARING`
  sends conflicting vehicles and all pedestrians to red (the route approach
  keeps its programme colour); `PRIORITY_GREEN` gives the route approach
  green and holds everything else red, pedestrians included; `RECOVERY` and
  `NORMAL` follow the programme. A disabled run therefore only ever shows the
  normal programme.
- Shown vehicle lights only change `GREEN -> YELLOW -> RED -> GREEN`: yellow
  lasts `signal_yellow_seconds`, and a light turns green only once every
  light not also turning green is red. These display constraints never
  change the programme colour used by motion. Yellow is always explicit in
  the payload; the dashboard never infers it.

The dashboard draws these indicators only above map zoom 16.5 (beyond the
route fit), each with its colour and a visible "SIM CAR/PED <colour>" label
plus `accessible_label`. Each intersection's indicators are stacked in a
deterministic column (one label height apart) so nearby signals never
overlap. Below that zoom it shows the per-intersection state dots; at
detail zoom an intersection without indicators keeps its dot, labelled
"SIM PHASES N/A" (and "simulated phase detail unavailable" for assistive
technology), instead of disappearing.

### Phase 3: Simulated ITS Dispatch (Internal `ItsGateway` Interface)

Triggered internally via a Python `ItsGateway` interface (with a mock
implementation that logs and records the dispatch event, rather than an
HTTP loop to itself) when an intersection transitions to `CLEARING`
($\mathrm{TTI}_i \le 40\text{ s}$ or via cascade). Only runs with
`green_wave_mode: "ENABLED"` dispatch. Uses the ETL-generated
`INT-xxxx` identifiers. One dispatch is made per tick and contains every
intersection that entered `CLEARING` in that tick (the TTI-triggered ones
and their cascade group); `message_id` is `MSG-ITS-<n>`, numbered per
simulation. The dispatch is also streamed as an `ITS_DISPATCH` event
(the fields below plus `event_type`, `tick`, `timestamp`).

`hold_duration_sec = max(40, ceil(TTI at dispatch) + 5)`, where for a group
the TTI is the **largest** in the group and 5 s is `its_hold_buffer_seconds`
(engine configuration, not a contract field). The hold covers the window
from `CLEARING` through `PRIORITY_GREEN` until the vehicle clears the stop
line; a fixed 40 s expired before the vehicle reached cascaded
intersections. `expected_arrival_utc` is the emission time plus the
**smallest** TTI in the group.

```json
{
  "schema_version": "1.0",
  "is_simulated": true,
  "event_type": "ITS_DISPATCH",
  "message_id": "MSG-ITS-88392",
  "simulation_id": "SIM-20261025-01",
  "tick": 30,
  "timestamp": "2026-10-25T14:31:58Z",
  "system_source": "ER_GREENWAVE_ENGINE",
  "target_system": "STeR_KRAKOW_ITS",
  "payload": {
    "priority_level": 1,
    "vehicle_type": "AMBULANCE",
    "intersections_group": ["INT-0360", "INT-0366"],
    "action": "FORCE_GREEN_PHASE",
    "hold_duration_sec": 55,
    "expected_arrival_utc": "2026-10-25T14:32:38Z"
  }
}
```

Here INT-0360 has TTI 40 s and its cascaded neighbour INT-0366 has TTI
50 s: the hold is `max(40, 50 + 5) = 55`. `hold_duration_sec` is never
below 40.

## 5. Proof-of-Concept Scope and Safety Note

ER-GreenWave is a proof of concept. Its ITS integration is mocked and
the JSON payloads illustrate the proposed interface; they do not
establish compatibility with Kraków's production traffic-control
infrastructure. Any real-world deployment would require validation with
the relevant authorities, controller-specific integration, and rigorous
operational and safety testing. All traffic signal states, delays and
priority dispatches are simulated inputs and do not represent verified
physical traffic signal states.

## 6. Resolved Architecture Decisions (Formerly Open Questions)

All previously open questions have been resolved and approved:

1. **State machine:** Intersection `state` is strictly `NORMAL | CLEARING | PRIORITY_GREEN | RECOVERY`, with `is_cascade: bool` as a separate field. Transitions occur at $\mathrm{TTI} \le 40\text{ s}$ (`CLEARING`), $\mathrm{TTI} \le 25\text{ s}$ (`PRIORITY_GREEN`), $d_i \le 0\text{ m}$ once the vehicle has left the last stop line and the tick carrying it across has been shown (`RECOVERY`, section 4, rule 3), and $+15\text{ s}$ (`NORMAL`). Cascade is one hop only (section 4, rule 1). `CLEARING_CASCADE` is not a state. `hold_duration_sec = max(40, ceil(TTI at dispatch) + its_hold_buffer_seconds)` with `its_hold_buffer_seconds = 5` (section 4, Phase 3).
2. **Identifiers:** All endpoints, telemetry ticks, and mock ITS payloads use the ETL's `INT-0001`..`INT-0534` IDs (`intersection_ids.json`). No `MSIP-SIG-*` IDs are used.
3. **Contract completeness:** `simulation_id`, `schema_version: "1.0"`, and `is_simulated: true` are included in all responses and ticks; streaming uses SSE (`GET /api/v1/simulation/{simulation_id}/stream`) with a cancel endpoint (`POST /api/v1/simulation/{simulation_id}/stop`); one active operation (a run or a lockstep comparison pair, ADR 0008) is supported at a time; ambulance `status` is `EN_ROUTE | APPROACHING_INTERSECTION | CROSSING_INTERSECTION | ARRIVED`; `traffic_density_multiplier` is bounded to `[1.0, 3.0]`.
4. **ITS dispatch (Phase 3):** Implemented as an internal Python `ItsGateway` interface with a mock implementation (no self-HTTP calls).
5. **Model inputs:** $V_{\mathrm{ambulance}}(e) = \min(\max(1.3 \cdot V_e \cdot b(e), 30.0), 90.0)\text{ km/h}$ with the road-attribute factors of section 3 (ADR 0005); $v_{\mathrm{avg}}$ uses an EMA ($\alpha = 0.25$, floored at $5.0\text{ m/s}$); all distance work is in `EPSG:2178` metres.
6. **Data sources:** Pinned BBBike OSM extract (`planet_19_792_50_012_71450a13_osm.geojson`) for road network and signals, paired with Kraków Open Data (`Ulice.geojson`, used for street names and cross-checks), tracked with hashes, licences and attribution in `backend/data/raw/MANIFEST.json`. No separate MSIP traffic-signal layer is used. The bus-lane CSV (`Buspasy_*.csv`, no geometry) is a cross-check only: its rows are matched by street name against OSM bus-lane edges (`bus_lane_crosscheck.csv`) and never change the network; bus lanes, tram tracks, lanes, surface and traffic calming come from OSM. The KMK lines CSV is recorded in the manifest but parked (no streets or geometry). Licence and attribution wording is settled (see "Data sources and attribution").
7. **Terminology:** `STeR_KRAKOW_ITS` is retained as the mocked target name.
8. **Intersection delay:** $D_u$ (35 s per kind via ETL configuration) and $D_{\min}$ (3 s) are applied once per unique `INT-xxxx` whose controlled approach the route passes, never per signal node or per approach. The ETL provides `delay_seconds` per intersection by kind (signalised junction and mid-block signal use the signal delay, a standalone pedestrian crossing the crossing delay).
9. **Cascade distance:** the threshold is `d <= 250 m` (inclusive) along the active route, measured between stop lines. The ETL's neighbour table uses the same inclusive threshold by shortest drive and is a candidate set only.
10. **Snapping:** the origin and destination snap to the nearest graph node (EPSG:2178) from which a route exists. A snap distance above **150 m** (engine configuration `max_snap_distance_meters`, not a contract field) is rejected with `ORIGIN_OFF_NETWORK` / `DESTINATION_OFF_NETWORK`.
11. **Contract v1:** the stream event union, SSE framing, error codes, `playback_speed` and the remaining simulation semantics are recorded in `docs/adr/0003-simulation-contract-v1.md`. Its D9 (1 Hz wall-clock tick advancing `playback_speed` seconds) is superseded: every simulated second is streamed as its own tick and playback only shortens the wall-clock interval (section 4, Phase 1). The wire schema is unchanged.
12. **ER Green Wave mode (additive to contract v1, `schema_version` stays `"1.0"`):** the start request and response carry `green_wave_mode: ENABLED | DISABLED` (closed enum, no boolean form; default `ENABLED`), and ticks carry `signal_phases` (default `[]`). Disabled runs use the standard-traffic crossing (section 3, model 3), stay `NORMAL`, never cascade or dispatch, and keep route choice and open-road motion identical to enabled runs. Signal phases are a simulated explanation drawn only at high zoom (section 4, Phase 2). The frontend has six destinations: home (`/`), enabled simulation (`/simulation/green-wave`), disabled simulation (`/simulation/standard`), recorded comparison (`/compare`), diagnostics (`/diagnostics`) and driver presentation (`/driver`). A root runtime owns one subscription and shared in-memory scenario across navigation. Comparison captures enabled then disabled sequentially through the same exclusive operation slot, then replays complete recordings on a common simulated clock; it never runs concurrent backend sessions. The completed-run summary leads with total travel time and names the mode. Design: `docs/superpowers/specs/2026-10-20-er-green-wave-mode-design.md`, amended by `docs/superpowers/specs/2026-10-21-er-green-wave-corrections-design.md` (rolling disabled crossing, supported signal movements, phase-detail fallback).
13. **Server-side run failure (additive to contract v1, `schema_version` stays `"1.0"`):** if the simulation loop fails, the server logs it and ends the run with `SIMULATION_CANCELLED` (`reason: SERVER_ERROR`, the last completed tick) like any other terminal, so clients learn at once instead of after their silence timeout. The dashboard shows "Simulation server error. Retry the green corridor initialization.", which is also shown when a start fails with HTTP 5xx. Retry is manual from dispatch setup; the mock never emits it. Decision: `docs/adr/0007-server-error-cancel-reason.md`.
