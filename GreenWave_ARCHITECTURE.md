# ER-GreenWave: Emergency Response GreenWave System

**Project developed for the "Open Data App" Hackathon (Kraków)**

ER-GreenWave is a proof-of-concept (PoC) platform demonstrating dynamic
routing and preemptive traffic-light clearing for emergency vehicles.
Using open spatial data from the City of Kraków, the system creates
temporary "green corridors" (life corridors) to reduce emergency
response times without compromising civilian traffic safety.

## 1. Glossary and Acronyms

- **TTI (Time to Intersection):** The dynamically calculated time
  remaining before the emergency vehicle reaches a specific
  intersection.
- **ITS (Intelligent Transportation System):** Centralized city
  systems that manage traffic lights. In Kraków, this refers to the
  STeR system.
- **MSIP (Miejski System Informacji Przestrzennej):** Kraków's
  official municipal spatial information system. In this project it is
  the publisher of the municipal street registry (`Ulice.geojson`) and
  of the other Kraków open-data files recorded in the raw-data manifest.
  It is not the source of the road network or of the traffic signals
  (these come from OpenStreetMap, see section 6, decision 6).
- **ZDMK (Zarząd Dróg Miasta Krakowa):** Kraków's municipal road
  authority; named as a publisher of the bus-lane data that is recorded
  in the manifest but not used by the PoC.
- **INT-xxxx:** An intersection identifier generated by the ETL
  (`INT-0001`..`INT-0534`): a signalised junction, a mid-block signal or
  a standalone signalised pedestrian crossing.
- **D_v / D_u:** The delay of one intersection without priority (35 s
  per kind in the current configuration), applied once per unique
  `INT-xxxx` whose controlled approach the route passes.
- **Datex II / NTCIP 1211:** Standards associated with communication
  and priority control in intelligent transportation systems.
- **SSE (Server-Sent Events) / WebSockets:** Technologies for
  streaming real-time data from the backend to the frontend,
  respectively unidirectionally or bidirectionally.
- **PoC (Proof of Concept):** A scaled-down implementation built to
  validate core logic and technical feasibility.

## 2. Architecture and Technology Stack

The project uses a decoupled architecture with a JSON-based
publish/subscribe contract. This supports rapid iteration, clear
separation of concerns, and straightforward integration with AI coding
assistants.

### Technology Stack

- **Backend:** Python and **FastAPI** (asynchronous event loop), with
  dependencies managed by **`uv`**.
- **Data processing engine:** **GeoPandas**, **Polars**, and
  **NetworkX** for graph-based pathfinding and spatial joins.
- **Frontend:** **Next.js** (React), **Tailwind CSS**, and
  **shadcn/ui** for dashboard development; run locally for the demo.
- **Mapping engine:** **MapLibre GL JS** (free, token-free fork of Mapbox GL; OSM-based tiles) for GPU-accelerated WebGL
  rendering of vehicle routes and intersection states.

### Architectural Decisions: Why?

1.  **Mocking the ITS controller:** The PoC does not interface directly
    with physical traffic lights because physical overrides are
    safety-critical. Instead, the system acts as an analytical layer
    that sends standardized priority requests to a mocked central ITS.
2.  **JSON contracts over WebSockets/SSE:** The frontend is passive and
    stateless. It consumes a data stream at 1 Hz and renders the
    interface, keeping UI complexity low.
3.  **Precomputed graph (ETL):** The pinned BBBike OpenStreetMap
    extract (road network and traffic signals) and the Kraków open-data
    street registry (`Ulice.geojson`), both tracked with hashes in
    `backend/data/raw/MANIFEST.json`, are processed by an offline ETL
    step (output cached in `backend/data/processed/`, never committed)
    into a directed NetworkX graph (`MultiDiGraph`, EPSG:2178 metres)
    plus the intersection, signal-approach and neighbour tables that the
    server loads once at startup. The loader refuses to start when an
    artifact is missing, was built from a different manifest, or comes
    from a different ETL run (per-artifact hashes); there is no
    fallback. Performing real-time pathfinding directly on raw GIS data
    would be too slow.
4.  **Corridor batching (cascade mode):** Clearing a single intersection
    on a dense street (such as Aleje Trzech Wieszczów) is ineffective if
    traffic is blocked at another intersection 150 m ahead. The engine
    groups consecutive intersections along the active route (along-route
    stop-line distance **d <= 250 m**, inclusive) and triggers them
    together. The ETL ships a candidate table of approach pairs within
    250 m by shortest drive (`approach_neighbours`); it is only a
    candidate set, and the engine decides with the along-route distance
    on the actual route.

## 3. Mathematical Models and Core Logic

### Time to Intersection (TTI)

TTI is recalculated every second (1 Hz tick) to drive the intersection state machine:

$$\mathrm{TTI}_i = \frac{d_i}{v_{\mathrm{avg}}}$$

Where:
- $d_i$ is the remaining distance (in metres, calculated in EPSG:2178) along the active route polyline to the first controlled approach stop line of intersection $i$.
- $v_{\mathrm{avg}}$ is the smoothed velocity of the ambulance (in $\text{m/s}$), computed as an exponential moving average $v_{\mathrm{avg}, t} = 0.25 \cdot v_t + 0.75 \cdot v_{\mathrm{avg}, t-1}$ (initialized to $v_0$ on the starting edge and floored at $5.0\text{ m/s}$ to prevent division by zero).

### Travel-Time Estimation Algorithm

The system compares normal routing with ER-GreenWave routing to estimate potential time savings (converting $L_e$ in metres and speeds in $\text{km/h}$ to seconds via $\text{speed}_{\mathrm{m/s}} = \text{speed}_{\mathrm{km/h}} / 3.6$):

#### 1. Normal travel time (without priority)

$$T_{\mathrm{normal}} = \sum_{e \in \mathrm{Edges}} \left( \frac{L_e \cdot \mu_{\mathrm{traffic}} \cdot f_{\mathrm{lane}}(e) \cdot f_{\mathrm{surface}}(e)}{V_e} + n_e \cdot s_{\mathrm{normal}} \right) + \sum_{u \in \mathrm{Intersections}} D_u$$

Where $V_e$ is the edge speed (`speed_kmh`: the OSM `maxspeed` where it parses, otherwise a road-class default, recorded in `speed_source`), $\mu_{\mathrm{traffic}} \in [1.0, 3.0]$ is the traffic-density multiplier ($\mu_{\mathrm{traffic}} = 1.0$ is free-flow; $1.5$ increases edge traversal time by 50%), and $D_u$ is the delay of intersection $u$ (`delay_seconds` in the ETL's `intersections` table, 35 s for every kind in the current configuration). $D_u$ is applied once per unique intersection (`INT-xxxx`) whose controlled approach the route passes: a route that passes two approaches of one intersection pays it once, and the per-signal `signal_approaches.delay_seconds` is never summed along a route.

Road attributes per directed edge (ETL, `network_edges.parquet`): $f_{\mathrm{lane}}(e) = 1.15$ when `lanes_per_direction == 1`, else 1; $f_{\mathrm{surface}}(e) = 1.3$ when `surface_class == "unpaved"`, else 1; $n_e$ is `calming_count` (OSM `traffic_calming` points on the edge) and $s_{\mathrm{normal}} = 3\text{ s}$ per feature. An unknown attribute has no effect. Values and evidence: `docs/adr/0005-road-attribute-time-factors.md`.

#### 2. ER-GreenWave travel time (with priority)

$$T_{\mathrm{greenwave}} = \sum_{e \in \mathrm{Edges}} \left( \frac{L_e}{V_{\mathrm{ambulance}}(e)} + n_e \cdot s_{\mathrm{ambulance}} \right) + \sum_{u \in \mathrm{Intersections}} D_{\min}$$

Where $V_{\mathrm{ambulance}}(e) = \min(\max(1.3 \cdot V_e \cdot b(e),\; 30\text{ km/h}),\; 90\text{ km/h})$, $b(e)$ is the **largest** applicable boost (not the product; 1 when none applies): 1.05 on a `bus_lane` edge, 1.05 on a `tram_track` edge; $s_{\mathrm{ambulance}} = 2\text{ s}$ per calming feature; and $D_{\min} = 3\text{ s}$ is applied once per unique intersection (`INT-xxxx`) whose controlled approach the route passes, by the same rule as $D_u$.

One edge-time function (`backend/src/greenwave/routing/edge_times.py`) drives route choice (minimum ambulance edge time), both estimates and simulated motion: on each edge the simulated ambulance moves at the effective speed $L_e / t_a(e)$ with $t_a(e) = L_e / V_{\mathrm{ambulance}}(e) + n_e \cdot s_{\mathrm{ambulance}}$, so calming seconds are spread over the edge and the simulated trip matches $T_{\mathrm{greenwave}}$ (except that a route ending exactly on a stop line arrives before that last $D_{\min}$). All factors are `GREENWAVE_SIM_*` settings; 1.0 / 0 s makes an attribute neutral.

## 4. Data Flow and JSON Protocols

The system uses explicit JSON schemas as the API contract between the
engine and the dispatcher dashboard. Only one active simulation runs at
a time in the PoC (starting a new simulation cancels any previous run).
All outputs are simulated inputs and include `"is_simulated": true`.
Every response and stream event also carries `"schema_version": "1.0"`.
The contract is frozen as `contract-v1` (see `docs/adr/0003-simulation-contract-v1.md`).
The intersection ids and names in the examples are real ETL output (two
consecutive junctions on Aleja 29 Listopada, about 152 m apart by
shortest drive); coordinates, times and speeds are illustrative.

### Intersection State Machine & Cascade Rules

Each intersection (`INT-xxxx`) along the active route transitions through
four states (`NORMAL | CLEARING | PRIORITY_GREEN | RECOVERY`), with a
separate boolean flag (`is_cascade: true | false`) indicating whether
the transition was triggered early by an upstream intersection within
`d <= 250 m` along the route:

1. **`NORMAL -> CLEARING`:** Triggered when $\mathrm{TTI}_i \le 40\text{ s}$
   (`is_cascade: false`), OR when an upstream intersection $j$ along the
   route enters `CLEARING` **because its own** $\mathrm{TTI}_j \le 40\text{ s}$
   (`is_cascade: false`) and the along-route distance from the stop
   line of $j$'s controlled approach to the stop line of $i$'s is
   $\le 250\text{ m}$ (`is_cascade: true`). Cascade is **one hop only**:
   an intersection that entered `CLEARING` through a cascade
   (`is_cascade: true`) never triggers a further cascade. Cascade looks
   only ahead along the route (never at an intersection already passed
   or behind $j$), uses the inclusive 250 m threshold measured from
   $j$ itself, and is disabled when `enable_cascade_mode` is `false`.
   Every other intersection still enters `CLEARING` by its own TTI. If an
   intersection reaches $\mathrm{TTI} \le 40\text{ s}$ in the same tick in
   which it would be cascaded, its own TTI wins (`is_cascade: false`).
   `CLEARING_CASCADE` is **not** a state; a cascaded intersection is
   `state: "CLEARING"` with `is_cascade: true`.
2. **`CLEARING -> PRIORITY_GREEN`:** Triggered when $\mathrm{TTI}_i \le 25\text{ s}$.
3. **`PRIORITY_GREEN -> RECOVERY`:** Triggered immediately when the
   ambulance passes the intersection's last controlled approach stop
   line ($d_i \le 0\text{ m}$).
4. **`RECOVERY -> NORMAL`:** Triggered $15\text{ s}$ after entering
   `RECOVERY`.

`is_active_corridor` is `true` exactly when `state` is `CLEARING` or
`PRIORITY_GREEN` (computed by the backend).

### Phase 1: Route Initialization (Frontend → Backend)

**Endpoint:** `POST /api/v1/simulation/start`

Called when the user selects the origin and destination.
`traffic_density_multiplier` must be in `[1.0, 3.0]`.

**Request:**

```json
{
  "simulation_id": "SIM-20261025-01",
  "origin": {
    "lat": 50.0612,
    "lng": 19.9571
  },
  "destination": {
    "lat": 50.0134,
    "lng": 19.9982
  },
  "traffic_density_multiplier": 1.5,
  "enable_cascade_mode": true,
  "playback_speed": 1
}
```

`simulation_id` is chosen by the client and must match
`^[A-Za-z0-9_-]{1,64}$`. `playback_speed` is optional (integer `1..10`,
default `1`): the wall-clock tick stays at 1 Hz and each tick advances
`playback_speed` simulated seconds, evaluated as 1 s sub-steps so no
threshold (40 / 25 / 0 / 15 s) is skipped.

**Response:** Returns static graph and route data.

```json
{
  "schema_version": "1.0",
  "is_simulated": true,
  "simulation_id": "SIM-20261025-01",
  "status": "INITIALIZED",

      [19.9571, 50.0612],

    ]
  },
  "total_distance_m": 5400,
  "estimated_normal_time_sec": 780,
  "estimated_greenwave_time_sec": 380,
  "intersections_on_route": ["INT-0360", "INT-0366"],
  "route_intersections": [
    {
      "id": "INT-0360",
      "name": "Aleja 29 Listopada / Lublańska / Opolska",
      "kind": "signalised_junction",
      "position": { "lat": 50.0661, "lng": 19.9221 },
      "distance_along_route_m": 1480
    },
    {
      "id": "INT-0366",
      "name": "Aleja 29 Listopada / Jana Woronicza",
      "kind": "signalised_junction",
      "position": { "lat": 50.0655, "lng": 19.9243 },
      "distance_along_route_m": 1632
    }
  ],
  "origin_snapped": {
    "position": { "lat": 50.0611, "lng": 19.9568 },
    "snap_distance_m": 12.4
  },
  "destination_snapped": {
    "position": { "lat": 50.0136, "lng": 19.9979 },
    "snap_distance_m": 31.7
  }

```

`route_intersections` lists every unique intersection on the route in
route order (`distance_along_route_m` is the distance to its first
controlled stop line); `intersections_on_route` carries the same ids.
`name` is `null` when the ETL has no name. `kind` is
`signalised_junction | midblock_signal | pedestrian_crossing`.
`origin_snapped` / `destination_snapped` give the graph point the route
really starts / ends at and its distance from the requested point.

**Errors** (body `ErrorResponse`):

```json
{
  "schema_version": "1.0",
  "error_code": "ORIGIN_OFF_NETWORK",
  "message": "Origin is 412 m from the nearest routable road; the limit is 150 m."
}
```

| `error_code` | HTTP | When |
|---|---|---|
| `ORIGIN_OFF_NETWORK` | 422 | Origin farther than the snap limit (150 m, section 6) from the network |
| `DESTINATION_OFF_NETWORK` | 422 | Same for the destination |
| `NO_ROUTE` | 422 | Both ends snap but no route connects them |
| `SIMULATION_ID_IN_USE` | 409 | `simulation_id` already used by a session still held in memory |
| `SIMULATION_NOT_FOUND` | 404 | Stream or stop for an unknown `simulation_id` |

FastAPI's default `422` body is kept for request-schema violations
(multiplier outside `[1.0, 3.0]`, bad `simulation_id` pattern,
`playback_speed` outside `1..10`).

### Phase 2: Real-Time Telemetry Stream & Control (Backend ↔ Frontend)

- **Stream Endpoint (SSE, 1 Hz tick):** `GET /api/v1/simulation/{simulation_id}/stream`
- **Stop Endpoint:** `POST /api/v1/simulation/{simulation_id}/stop`

The frontend consumes the Server-Sent Events (SSE) stream to animate the
MapLibre vehicle marker and update dashboard KPIs. Ambulance `status` is
an enum of `EN_ROUTE | APPROACHING_INTERSECTION | CROSSING_INTERSECTION | ARRIVED`.

The stream carries a discriminated union on `event_type`:
`SIMULATION_TICK`, `ITS_DISPATCH`, `SIMULATION_COMPLETED`,
`SIMULATION_CANCELLED` (`reason: STOPPED | SUPERSEDED`). Every event has
`schema_version`, `is_simulated`, `simulation_id`, `tick` and `timestamp`
(wall-clock UTC at emission; simulated time is
`kpi_metrics.total_time_elapsed_sec`).

**SSE framing** (not expressible in OpenAPI, so normative here): the first
frame is `retry: 2000`. Each event is one frame with `event:` = its
`event_type`, `id:` = its `tick` (non-decreasing; ticks start at 1, an
`ITS_DISPATCH` shares the id of the tick that produced it and precedes that
tick's `SIMULATION_TICK`; a terminal event repeats the last tick id) and
`data:` = the JSON of one event model. The server closes the stream after
a terminal event (`SIMULATION_COMPLETED` or `SIMULATION_CANCELLED`).
A subscriber first receives the latest snapshot, then live events; a
reconnect resumes at "now" without replay. The run is server-authoritative:
it starts on `POST /start` and ticks whether or not anyone listens. After
`ARRIVED` the engine keeps ticking until every intersection is `NORMAL`
(at most 15 s), then emits `SIMULATION_COMPLETED`. A finished session stays
readable until superseded. `POST /stop` returns `StopResponse`
(`{"schema_version": "1.0", "is_simulated": true, "simulation_id": ..., "status": "STOPPED"}`).

**`SIMULATION_TICK`:**

```json
{
  "schema_version": "1.0",

  "simulation_id": "SIM-20261025-01",
```

### Phase 3: Simulated ITS Dispatch (Internal `ItsGateway` Interface)

Triggered internally via a Python `ItsGateway` interface (with a mock
implementation that logs and records the dispatch event, rather than an
HTTP loop to itself) when an intersection transitions to `CLEARING`
($\mathrm{TTI}_i \le 40\text{ s}$ or via cascade). Uses the ETL-generated
`INT-xxxx` identifiers. One dispatch is made per tick and contains every
intersection that entered `CLEARING` in that tick (the TTI-triggered ones
and their cascade group); `message_id` is `MSG-ITS-<n>`, numbered per
simulation. The dispatch is also streamed as an `ITS_DISPATCH` event
(the fields below plus `event_type`, `tick`, `timestamp`).

`hold_duration_sec = max(40, ceil(TTI at dispatch) + 5)`, where for a group
the TTI is the **largest** in the group and 5 s is `its_hold_buffer_seconds`
(engine configuration, not a contract field). The hold covers the window
from `CLEARING` through `PRIORITY_GREEN` until the vehicle clears the stop
line; a fixed 40 s expired before the vehicle reached cascaded
intersections. `expected_arrival_utc` is the emission time plus the
**smallest** TTI in the group.

```json
{
  "schema_version": "1.0",
  "is_simulated": true,
  "event_type": "ITS_DISPATCH",
  "message_id": "MSG-ITS-88392",
  "simulation_id": "SIM-20261025-01",
  "tick": 30,
  "timestamp": "2026-10-25T14:31:58Z",
  "system_source": "ER_GREENWAVE_ENGINE",
  "target_system": "STeR_KRAKOW_ITS",
  "payload": {
    "priority_level": 1,
    "vehicle_type": "AMBULANCE",
    "intersections_group": ["INT-0360", "INT-0366"],
    "action": "FORCE_GREEN_PHASE",
    "hold_duration_sec": 55,
    "expected_arrival_utc": "2026-10-25T14:32:38Z"
  }
}
```

Here INT-0360 has TTI 40 s and its cascaded neighbour INT-0366 has TTI
50 s: the hold is `max(40, 50 + 5) = 55`. `hold_duration_sec` is never
below 40.

## 5. Proof-of-Concept Scope and Safety Note

ER-GreenWave is a proof of concept. Its ITS integration is mocked and
the JSON payloads illustrate the proposed interface; they do not
establish compatibility with Kraków's production traffic-control
infrastructure. Any real-world deployment would require validation with
the relevant authorities, controller-specific integration, and rigorous
operational and safety testing. All traffic signal states, delays and
priority dispatches are simulated inputs and do not represent verified
physical traffic signal states.

## 6. Resolved Architecture Decisions (Formerly Open Questions)

All previously open questions have been resolved and approved:

1. **State machine:** Intersection `state` is strictly `NORMAL | CLEARING | PRIORITY_GREEN | RECOVERY`, with `is_cascade: bool` as a separate field. Transitions occur at $\mathrm{TTI} \le 40\text{ s}$ (`CLEARING`), $\mathrm{TTI} \le 25\text{ s}$ (`PRIORITY_GREEN`), $d_i \le 0\text{ m}$ (`RECOVERY`), and $+15\text{ s}$ (`NORMAL`). Cascade is one hop only (section 4, rule 1). `CLEARING_CASCADE` is not a state. `hold_duration_sec = max(40, ceil(TTI at dispatch) + its_hold_buffer_seconds)` with `its_hold_buffer_seconds = 5` (section 4, Phase 3).
2. **Identifiers:** All endpoints, telemetry ticks, and mock ITS payloads use the ETL's `INT-0001`..`INT-0534` IDs (`intersection_ids.json`). No `MSIP-SIG-*` IDs are used.
3. **Contract completeness:** `simulation_id`, `schema_version: "1.0"`, and `is_simulated: true` are included in all responses and ticks; streaming uses SSE (`GET /api/v1/simulation/{simulation_id}/stream`) with a cancel endpoint (`POST /api/v1/simulation/{simulation_id}/stop`); one active simulation is supported at a time; ambulance `status` is `EN_ROUTE | APPROACHING_INTERSECTION | CROSSING_INTERSECTION | ARRIVED`; `traffic_density_multiplier` is bounded to `[1.0, 3.0]`.
4. **ITS dispatch (Phase 3):** Implemented as an internal Python `ItsGateway` interface with a mock implementation (no self-HTTP calls).
5. **Model inputs:** $V_{\mathrm{ambulance}}(e) = \min(\max(1.3 \cdot V_e \cdot b(e), 30.0), 90.0)\text{ km/h}$ with the road-attribute factors of section 3 (ADR 0005); $v_{\mathrm{avg}}$ uses an EMA ($\alpha = 0.25$, floored at $5.0\text{ m/s}$); all distance work is in `EPSG:2178` metres.
6. **Data sources:** Pinned BBBike OSM extract (`planet_19_792_50_012_71450a13_osm.geojson`) for road network and signals, paired with Kraków Open Data (`Ulice.geojson`, used for street names and cross-checks), tracked with hashes, licences and attribution in `backend/data/raw/MANIFEST.json`. No separate MSIP traffic-signal layer is used. The bus-lane CSV (`Buspasy_*.csv`, no geometry) is a cross-check only: its rows are matched by street name against OSM bus-lane edges (`bus_lane_crosscheck.csv`) and never change the network; bus lanes, tram tracks, lanes, surface and traffic calming come from OSM. The KMK lines CSV is recorded in the manifest but parked (no streets or geometry). Licence and attribution wording is settled (see "Data sources and attribution").
7. **Terminology:** `STeR_KRAKOW_ITS` is retained as the mocked target name.
8. **Intersection delay:** $D_u$ (35 s per kind via ETL configuration) and $D_{\min}$ (3 s) are applied once per unique `INT-xxxx` whose controlled approach the route passes, never per signal node or per approach. The ETL provides `delay_seconds` per intersection by kind (signalised junction and mid-block signal use the signal delay, a standalone pedestrian crossing the crossing delay).
9. **Cascade distance:** the threshold is `d <= 250 m` (inclusive) along the active route, measured between stop lines. The ETL's neighbour table uses the same inclusive threshold by shortest drive and is a candidate set only.
10. **Snapping:** the origin and destination snap to the nearest graph node (EPSG:2178) from which a route exists. A snap distance above **150 m** (engine configuration `max_snap_distance_meters`, not a contract field) is rejected with `ORIGIN_OFF_NETWORK` / `DESTINATION_OFF_NETWORK`.
11. **Contract v1:** the stream event union, SSE framing, error codes, `playback_speed` and the remaining simulation semantics are recorded in `docs/adr/0003-simulation-contract-v1.md`.
